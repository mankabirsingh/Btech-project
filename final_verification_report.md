### 2.4 Duplicate and Near-Duplicate Cross-Split Audit

We conducted both an exact match check and an exhaustive near-duplicate similarity search:

1. **Exact Duplicate Overlap Across Splits:**
   - $\text{Train} \cap \text{Val} = \emptyset$ (**0 exact matches**)
   - $\text{Train} \cap \text{Test} = \emptyset$ (**0 exact matches**)
   - $\text{Val} \cap \text{Test} = \emptyset$ (**0 exact matches**)
2. **Near-Duplicate Similarity Analysis:**
   - Evaluated 1,000,000 random train-test pairs using character 4-gram Jaccard similarity ($J$).
   - Found **8 pairs** with $J \ge 0.85$ ($0.0008\%$).
   - **Root Cause Analysis:** These 8 pairs represent identical or near-identical C functions modified across *different historical commits* within large repositories (e.g., `pxa255_init` in QEMU touched in commit `b45c03f` in the test split and commit `c92cfba` in the train split). Because each commit received a distinct commit hash, commit-level grouping placed them in different splits.
   - **Scientific Implication:** Commit-level grouping strictly eliminates *intra-commit patch leakage* (preventing pre-patch/post-patch memorization). However, over the 15-year histories of QEMU and FFmpeg, identical functions touched across different CVE commits can cross splits unless grouping is performed at the *function-symbol* or *repository* level.

### 2.5 Preprocessing and Feature Selection Leakage
- `clean_c_code` applies deterministic regex-based whitespace normalization and comment removal. It processes each function in strict isolation without dataset-level statistics.
- TF-IDF vectorizers (`TfidfVectorizer`) are fit strictly on `vulnerability_train.parquet`. Validation and test splits are transformed using the frozen training vocabulary.
- In `src/models/code_encoder.py`, the previous feature extractor extracted `has_cwe = df['cwe'].notna()`. In Devign, only vulnerable functions have CWE labels, creating direct target leakage. **Verification confirmed this has been removed**. Current provenance features rely exclusively on comment ratio, line counts, character length, and simulated author metadata. Zero target information is leaked.

## 4. Critical Audit of the Provenance Experiment

We audited `scripts/train_provenance_experiment.py`, `scripts/run_controlled_experiment.py`, and the resulting data artifacts.

### 4.1 Track 1: Real-World Open-Source Benchmark (Devign + PrimeVul)
- **Dataset:** 5,412 held-out real-world C/C++ functions from Devign and PrimeVul.
- **Model A (Code-Only):** Logistic regression trained on word TF-IDF features.
- **Model B (Code + Provenance):** Logistic regression trained on word TF-IDF + provenance features (`ai_involvement`, `author_type`, `num_edits`, `code_length`, `comment_ratio`).
- **Results:**
  - Model A: Accuracy **49.70%**, F1 **50.31%**, AUROC **0.5095**
  - Model B: Accuracy **50.39%**, F1 **51.19%**, AUROC **0.5129**
  - Difference ($\Delta$): **+0.69% Accuracy**, **+0.0034 AUROC**
- **Audit Assessment:**
  - Both models use the exact same test split.
  - Model A is a genuine ML baseline.
  - Feature extraction is clean and contains zero target label leakage.
  - **Empirical Reality:** The gain is negligible (+0.69%) because real-world open-source codebases (QEMU, FFmpeg, Linux) are historically 100% human-authored ($\text{AI Involvement} = 0.0$). Provenance metadata provides no signal on legacy code.

### 4.2 Track 2: Controlled Multi-CWE Benchmark (8 Tasks, 32 Versions)
We examined the 32-sample benchmark spanning 8 major CWE categories (CWE-120, CWE-134, CWE-190, CWE-78, CWE-416, CWE-22, CWE-327, CWE-476). Each task has 4 versions:
- $v_1$: Human baseline (secure, $\text{AI} = 0.0$, label = 0)
- $v_2$: AI generation (vulnerable, $\text{AI} = 1.0$, label = 1)
- $v_3$: Human remediation (secure, $\text{AI} = 0.5$, label = 0)
- $v_4$: AI regression / incomplete patch (vulnerable, $\text{AI} = 0.75$, label = 1)
- Total: 16 vulnerable functions, 16 benign functions.

#### Investigation of the Claim: "Model B achieves 84.38% Acc and 100% Precision at 25% Review Budget"
- **How was the Provenance Score computed?**
  In `scripts/run_controlled_experiment.py`, the score is computed as:
  $$\text{Score}_{\text{prov}} = P_{\text{codebert}}(\text{vulnerable}) \times (0.6 + 0.8 \times \text{AI Involvement})$$
- **Is this a trained, generalizable model?**
  **NO.** It is an **explicit algebraic risk-weighting heuristic**. It is not an end-to-end trained deep neural network.
- **Why does it achieve 100% precision at 25% review budget?**
  - In the curated benchmark, every vulnerable sample has high AI involvement ($v_2 = 1.0$, $v_4 = 0.75$), while every secure sample has lower AI involvement ($v_1 = 0.0$, $v_3 = 0.50$).
  - When the code probability is scaled by $(0.6 + 0.8 \times \text{AI Involvement})$, the score multiplier for $v_2$ is $1.4\times$ and for $v_4$ is $1.2\times$, while for $v_1$ it is $0.6\times$ and for $v_3$ it is $1.0\times$.
  - Consequently, the top 8 ranked samples are virtually guaranteed to be $v_2$ and $v_4$ (all vulnerable), yielding **100% precision (8 / 8)** and **50% recall (8 / 16)** at a 25% review budget.

#### Methodological Verdict
| Question | Answer |
| :--- | :--- |
| Is this a trained, generalizable model? | **No.** It is a hand-designed ranking rule. |
| Is this a statistically significant proof on in-the-wild code? | **No.** It is a curated demonstration on 32 functions across 8 tasks. |
| What is the correct scientific interpretation? | It is an **effective proof-of-concept case study** illustrating how provenance metadata can be integrated into DevSecOps triage policies to prioritize AI-assisted code for security inspection. |

## 7. Remaining Limitations & Threats to Validity

1. **Curated Nature of Hybrid Benchmark:** The 32-sample benchmark is an illustrative proof-of-concept. Real-world human-AI hybrid code exhibits far noisier editing patterns and varying skill levels.
2. **Heuristic vs. End-to-End Learning:** The review prioritization score uses an explicit algebraic weighting formula rather than an end-to-end multi-modal neural network.
3. **Flat Sequence Modeling:** Pretrained CodeBERT operates on linear token sequences (up to 512 tokens), omitting program-dependence graphs (PDGs) and abstract syntax trees (ASTs).
4. **Cross-Commit Function Near-Duplicates:** While commit-level grouping eliminates intra-commit pair leakage, identical functions edited across different CVE commits in long-running projects can cross splits unless function-symbol grouping is enforced.
