## 1. Sample Size and Statistical Power of Controlled Benchmarks

- **Current Evaluation Volume:**
  - Locked Independent Evaluation Benchmark: 32 code units (8 tasks $\times$ 4 lineage versions).
  - Development Corpus: 64 code units (16 tasks $\times$ 4 lineage versions).
- **Statistical Uncertainty:**
  - While Model B achieved 96.88% accuracy (31/32 correct) on the locked benchmark, the 95% Wilson score confidence interval is $[84.3\%, 99.5\%]$.
  - The sample size of 32 units, while carefully balanced and multi-CWE (8 distinct CWEs), is small compared to traditional static codebases.
  - **Academic Boundary:** We explicitly disclose this small sample size and do NOT claim statistically definitive population-level conclusions across all millions of open-source software projects.

---

## 2. Controlled vs In-the-Wild Provenance Tracking

- **Nature of Benchmark Lineage:**
  - The 32 locked benchmark units and 64 development units were constructed in controlled settings with explicit human authoring, real AI assistant prompts (ChatGPT, GitHub Copilot, Claude 3.5), and documented human refactoring cycles.
  - While realistic and grounded in CVE-tested attack vectors, they are controlled experimental units rather than telemetry mined from large-scale enterprise IDE git histories.
- **Why In-The-Wild Mining is Blocked Today:**
  - Commercial IDE extensions (Copilot, Cursor) do not yet record public cryptographic commit attestations declaring the exact percentage of code generated by LLMs vs human typing.
  - As established in our dataset audit ([`reports/phase10_dataset_audit.md`](file:///Users/mankabir/Desktop/Btech%20project/reports/phase10_dataset_audit.md)), public CVE repositories (Devign, BigVul, PrimeVul) represent historical pre-2022 code with zero AI provenance.

## 3. The Human Author Bias Caveat

- **Risk of Over-Relying on Provenance:**
  - Model B learns that human review cycles mitigate risk ($\text{weight} = -3.6468$), while raw AI code elevates risk ($\text{weight} = +3.6471$).
  - *Failure Mode:* If a malicious developer intentionally commits an exploit under a "human author" label, or if a tired developer approves an AI suggestion without reading it, Model B might down-weight the audit priority if code-only signals are weak.
  - *Mitigation in our Architecture:* Model B enforces a non-zero lower bound based on Model A's base code probability and Flawfinder static analysis. When static security analysis identifies a high-severity flaw, Model B preserves the alert regardless of author claims.

---

## 4. Triage Priority vs Confirmed Vulnerability

- **Operational Distinction:**
  - Model B outputs a **vulnerability probability** and an **operational code-review priority tier** (`Tier-1 Urgent`, `Tier-2 Elevated`, `Tier-3 Standard`).
  - Neither output constitutes a mathematical proof of exploitability.
  - Static pattern matching and ML classification can highlight risk clusters, but dynamic validation (fuzzing, unit tests, symbolic execution) remains essential to confirm vulnerability reachability in production runtimes.

---

## 5. Next Concrete Steps for Future Work

1. **IDE Telemetry Integration:** Develop an open-source VSCode/Git hook extension that cryptographically signs git commits with keystroke-level human vs AI authorship metadata.
2. **Expansion to 256 Controlled Benchmarks:** Expand the controlled benchmark from 8 tasks to 64 tasks across 32 CWEs to narrow the statistical confidence intervals.
3. **AST-Level Token Attribution:** Rather than treating provenance as function-level percentages, track provenance at the individual Abstract Syntax Tree statement level.
